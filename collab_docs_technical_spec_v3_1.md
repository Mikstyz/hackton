# Техническая спецификация v3.1

## Сервис совместного редактирования документов

**Дата:** 07.11.2026\
**Backend:** Go\
**Frontend:** React + TypeScript\
**Редактор:** TipTap / ProseMirror\
**CRDT:** Yjs\
**Хранилище MVP:** SQLite WAL\
**Развёртывание:** Docker\
**Цель масштабирования:** архитектурная готовность к кластеру с 10 000
одновременных подключений. Фактическая ёмкость подтверждается
нагрузочными тестами.

> Это целевая архитектура, а не гарантия производительности. Численные
> лимиты ниже являются начальными параметрами для испытаний.

## 1. Назначение и концепция

Веб-приложение для совместной работы над документами в реальном времени.
Пользователи создают комнаты, приглашают участников по ссылке, создают
документы внутри комнаты или добавляют существующие. Участники
одновременно редактируют документы, видят курсоры, выделения и список
присутствующих. Изменения автоматически сохраняются, а после
переподключения или перезапуска сервера документ восстанавливается.

Основные требования:

1.  Создание комнаты и документа, ссылки для приглашения.
2.  Вход без регистрации с отображаемым именем.
3.  Индивидуальный цвет участника.
4.  Синхронизация текста и курсоров в реальном времени.
5.  Одновременное редактирование абзаца без блокировок.
6.  Подключение новых участников с получением актуального состояния.
7.  Автосохранение с достоверной индикацией.
8.  Восстановление после потери соединения и перезапуска.
9.  Возможность позднее добавить историю, diff и rollback.
10. Изоляция перегрузки и отказов отдельных клиентов и документов.

### 1.1. Модель предметной области

``` text
Application
└── Room
    ├── Participants
    └── Documents
        ├── Active CRDT state
        ├── CRDT update journal
        ├── Snapshots
        └── (Future) Commits / History
```

**Room** --- рабочее пространство, объединяющее участников и документы.\
**Document** --- самостоятельная единица синхронизации, сохранения и
версионирования.\
**Participant** --- анонимная сессия с именем и назначенным сервером
цветом.\
**DocActor** --- владелец runtime-состояния одного активного документа.

Комната остаётся сущностью продукта, но не должна быть единственной
единицей синхронизации: документы внутри неё обрабатываются независимо.
Пользователь может поделиться ссылкой на комнату или прямой ссылкой на
документ.

### 1.2. Приоритеты

-   **P0** --- обязательно для MVP.
-   **P1** --- желательно после проверки основного сценария.
-   **P2** --- последующее расширение.

### 1.3. Вне MVP

Полноценные Git-подобные commits, сложный структурный diff, rollback,
импорт DOCX, аккаунты, E2E-шифрование, Redis-кластер и Kubernetes не
должны задерживать MVP. Архитектура оставляет путь для их добавления.

### 2.1. Критическое решение по Yjs

Yjs --- JavaScript-библиотека. Зрелый клиентский Yjs не означает наличие
столь же зрелой Go-реализации.

Варианты:

1.  **Pure-Go порт Yjs.** Предпочтителен для единого Go backend, только
    если проходит interop-тесты с настоящим Yjs.
2.  **Слепой relay updates в Go.** Самый простой MVP, но сервер не может
    полноценно валидировать CRDT-состояние, вычислять state vector/diff
    и самостоятельно создавать snapshots.
3.  **CRDT sidecar.** Отдельный процесс на Node.js или Rust, если
    Go-порт не проходит проверку. Это добавляет эксплуатационную
    сложность.

**Gate до основной реализации:** проверить применение updates, state
vector, diff, snapshot, повторы, переупорядочивание и совместимость с
клиентским `yjs` и `y-protocols`.

Нельзя считать молодой Go-порт production-ready только потому, что он
компилируется. Если Go-порт не проходит тесты, не нужно писать CRDT с
нуля за конкурсное время: выбирается relay или sidecar с явно
зафиксированными компромиссами.

### 3.3. Владение состоянием

  Состояние                    Владелец
  ---------------------------- -------------------------------------
  Реестр комнат                Room Manager
  Реестр активных документов   Document Manager
  CRDT state                   DocActor / Engine
  `headSeq`, `persistedSeq`    DocActor / Persistence coordination
  Подключения документа        DocActor / Gateway
  Исходящая очередь клиента    WebSocket connection
  SQLite write connection      SQLite Writer
  Presence                     DocActor / Presence Manager
  Snapshots                    Snapshot Worker

Мьютексы допустимы для реестров и лимитеров. Не нужен глобальный mutex
вокруг всех документов. Порядок событий одного документа обеспечивает
его владелец состояния.

### 3.4. DocActor

У каждого активного документа есть последовательная обработка событий.
Разные документы работают независимо.

DocActor принимает валидированные события, применяет update через Engine
(если реализация это поддерживает), назначает серверный `seq`,
инициирует рассылку, ставит update в persistence queue, отслеживает
durable persistence, управляет Presence и инициирует выгрузку после
простоя.

Документы загружаются лениво. Неактивные можно выгружать после
сохранения. Нельзя создавать бесконечное число горутин и очередей без
admission control.

## 5. Функциональные требования

### 5.1. Комнаты

**P0:** создание комнаты; случайная ссылка-приглашение; вход по ссылке;
ввод имени; список документов; создание документа; добавление
существующего документа; список присутствующих; выход.

**P1:** отзыв ссылки; срок действия; read-only режим; лимиты участников;
расширенные права.

Комната остаётся в базе после ухода последнего участника.
Ссылка-приглашение является отдельной сущностью: у комнаты и документа
могут быть разные ссылки, каждая может иметь роль, срок действия и
отзыв.

### 5.2. Документы

**P0:** создание документа внутри комнаты; открытие по прямой ссылке;
проверка принадлежности комнате; совместное редактирование; получение
актуального состояния; сохранение и восстановление.

GET не должен создавать документ. Создание --- отдельный POST. У комнаты
и документа собственные идентификаторы и ссылки.

### 5.3. Анонимные сессии и цвета

После ввода имени сервер создаёт сессию и назначает цвет.

Рекомендуемые claims подписанного токена:

``` text
{
  version,
  session_id,
  room_id,
  document_scope,
  name,
  color,
  role,
  issued_at,
  expires_at,
  key_id
}
```

Токен подписывается HMAC-SHA256, ключи поддерживают ротацию через
`key_id`. Передача --- HttpOnly cookie с Secure и подходящим SameSite.

Имя нормализуется Unicode NFC, обрезается по краям, ограничивается,
например, 1--32 Unicode code points. Управляющие символы запрещаются.
Политика bidi/control символов задаётся явно.

Цвет выбирается сервером из палитры: например, наименее используемый
среди активных участников документа. Если палитра исчерпана,
генерируется отличающийся оттенок. Цвет стабилен в течение сессии.

Сервер переписывает поле `user` в awareness и не доверяет имени/цвету из
браузера.

### 5.4. Совместное редактирование

-   Передавать инкрементальные Yjs updates.
-   Не отправлять весь документ после каждого нажатия.
-   Не блокировать абзацы и диапазоны.
-   Обеспечивать сходимость при конкурентных изменениях.
-   Синхронизировать новых и переподключившихся участников.

Конфликты разрешаются CRDT. Сервер не реализует текстовую
OT-трансформацию.

### 5.5. Presence

Awareness содержит session ID, имя, цвет, client ID, курсор, выделение и
время последнего обновления.

Presence эфемерный и не записывается в SQLite. При отключении соединения
сервер удаляет awareness. Для зависших состояний используется timeout.

Курсоры агрегируются и рассылаются с ограниченной частотой, например не
более 20 Гц на документ. Это стартовое значение для тестов.

## 7. WebSocket-протокол `collab.v1`

Протокол --- общий контракт frontend/backend. Он хранится в репозитории
вместе с golden-векторами.

### 7.1. Транспорт

-   Один WebSocket обслуживает один документ.
-   Подпротокол: `collab.v1`.
-   CRDT и awareness используют бинарные кадры.
-   Размеры сообщений ограничены конфигурацией.
-   Origin и cookie проверяются до upgrade.
-   WebSocket compression выключен на старте; включать только после
    измерений.

Для совместимости payload синхронизации использовать формат
`y-protocols`, а не самодельный несовместимый формат.

### 7.2. Логические сообщения

  Тип             Направление       Назначение
  --------------- ----------------- ---------------------------------
  `SYNC_STEP1`    Both              Обмен state vector
  `SYNC_STEP2`    Both              Передача недостающего состояния
  `SYNC_UPDATE`   Both              Инкрементальное изменение
  `AWARENESS`     Both              Курсоры и Presence
  `ACK`           Server → Client   Durable persistence
  `NOTICE`        Server → Client   Деградация/восстановление
  `ERROR`         Server → Client   Ошибка протокола или доступа
  `PING/PONG`     Both              Контроль соединения

Нумерация типов, varuint-кодирование и точные байтовые форматы
фиксируются в `protocol/collab.v1.md`. Frontend и backend реализуют один
контракт.

### 7.3. Handshake без окна потерь

1.  Клиент устанавливает WebSocket.
2.  Сервер проверяет сессию и доступ.
3.  Запрос регистрации поступает в DocActor.
4.  DocActor фиксирует точку синхронизации и регистрирует клиента.
5.  Сервер отправляет state vector/начальное состояние.
6.  Клиент и сервер обмениваются недостающими updates.
7.  Updates после точки синхронизации доставляются через live-канал.
8.  Клиент завершает handshake.

Точная реализация зависит от Engine. Тест должен вносить изменения во
время handshake и проверять отсутствие потерянных операций.

### 7.4. Семантика ACK

Клиент различает локально созданные, отправленные и подтверждённо
сохранённые изменения.

-   `sent` --- последовательность отправленных операций текущего
    соединения.
-   `acked` --- подтверждённый префикс операций.
-   `persisted_seq` --- максимальный непрерывно сохранённый номер
    журнала документа.

Сервер связывает входящие сообщения с серверным seq. ACK подтверждает
только те клиентские операции, для которых соответствующие серверные
записи прошли COMMIT.

`Saved` разрешено только после завершения handshake и когда все
отправленные операции до текущей точки подтверждены.

Отображение `client sequence → document sequence` должно быть формально
описано и протестировано. Нельзя подтверждать только факт приёма или
рассылки.

Для повторной отправки клиент использует стабильный `update_id` в
локальной очереди. Сервер может дедуплицировать транспортные повторы.
Идемпотентность Yjs не отменяет раздувание журнала повторными INSERT.

### 7.5. Переподключение

Клиент хранит неподтверждённые updates в IndexedDB, применяет
exponential backoff с jitter и после reconnect синхронизирует локальное
состояние с сервером.

Предусмотреть коды закрытия для нормального выхода, перезапуска,
перегрузки, истёкшей сессии, нарушения протокола, слишком большого
сообщения и slow consumer.

## 8. Очереди и конкурентность Go

### 8.1. Поток обработки

``` text
WebSocket Readers
       |
       v
Bounded Document Inbox
       |
       v
DocActor / Engine
       |
       +---------------------+
       |                     |
       v                     v
Client Outboxes        Persistence Queue
       |                     |
       v                     v
WebSocket Writers       SQLite Writer
                             |
                             v
                        Snapshot Worker
```

### 8.2. Очереди

  -----------------------------------------------------------------------
  Очередь                 Назначение              Правило
  ----------------------- ----------------------- -----------------------
  Document Inbox          Входящие события        Ограниченная, порядок
                                                  внутри документа

  Client Outbox           Отправка клиенту        Отдельная на соединение

  Persistence Queue       Запись updates          Ограниченная, без
                                                  молчаливой потери

  Snapshot Queue          Snapshots               Фоновая и ограниченная

  Presence                Курсоры                 Coalescing допустим
  -----------------------------------------------------------------------

### 8.3. Backpressure

При заполнении очереди:

1.  Не удалять молча CRDT updates.
2.  Приостанавливать чтение от перегруженного клиента.
3.  Ограничивать частоту входящих сообщений.
4.  Отключать медленного получателя при длительном переполнении.
5.  Не подтверждать сохранение до COMMIT.
6.  При критическом переполнении временно отклонять новые операции.

Если БД недоступна, очередь не должна расти бесконечно. Система
переходит в degraded mode: не выдаёт `Saved`, ограничивает новые updates
и полагается на локальную очередь клиента.

### 8.4. SQLite Writer

Один логический writer сериализует транзакции одного SQLite-файла.
Producers могут работать параллельно.

Writer объединяет updates в batch. Flush выполняется по размеру batch,
таймеру и при shutdown. Batch нельзя очищать до успешного COMMIT. Ошибки
обрабатываются ограниченными повторами с backoff; после исчерпания
попыток сервер сообщает о деградации и не подтверждает сохранение.

## 9. SQLite и модель данных

### 9.1. Принципы

-   SQLite --- постоянное хранилище MVP.
-   Runtime-состояние активного документа находится в памяти.
-   Updates записываются в журнал.
-   Snapshots сокращают время восстановления.
-   Presence не сохраняется.
-   Commits добавляются отдельным этапом.

### 9.2. Стартовая схема

``` sql
PRAGMA foreign_keys = ON;

CREATE TABLE rooms (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL
);

CREATE TABLE documents (
    id TEXT PRIMARY KEY,
    title TEXT NOT NULL,
    head_seq INTEGER NOT NULL DEFAULT 0,
    persisted_seq INTEGER NOT NULL DEFAULT 0,
    snapshot_seq INTEGER NOT NULL DEFAULT 0,
    created_at INTEGER NOT NULL,
    updated_at INTEGER NOT NULL
);

-- Room and document are separate entities. The relation permits an existing
-- document to be attached to another room without duplicating CRDT state.
CREATE TABLE room_documents (
    room_id TEXT NOT NULL,
    document_id TEXT NOT NULL,
    added_at INTEGER NOT NULL,
    PRIMARY KEY (room_id, document_id),
    FOREIGN KEY (room_id) REFERENCES rooms(id) ON DELETE CASCADE,
    FOREIGN KEY (document_id) REFERENCES documents(id) ON DELETE CASCADE
);

CREATE INDEX idx_room_documents_document ON room_documents(document_id);

CREATE TABLE invite_links (
    id TEXT PRIMARY KEY,
    token_hash TEXT NOT NULL UNIQUE,
    scope_type TEXT NOT NULL CHECK (scope_type IN ('room', 'document')),
    room_id TEXT,
    document_id TEXT,
    role TEXT NOT NULL DEFAULT 'editor',
    expires_at INTEGER,
    revoked_at INTEGER,
    created_at INTEGER NOT NULL,
    FOREIGN KEY (room_id) REFERENCES rooms(id) ON DELETE CASCADE,
    FOREIGN KEY (document_id) REFERENCES documents(id) ON DELETE CASCADE,
    CHECK (
        (scope_type = 'room' AND room_id IS NOT NULL AND document_id IS NULL)
        OR
        (scope_type = 'document' AND room_id IS NULL AND document_id IS NOT NULL)
    )
);

CREATE INDEX idx_invite_links_room ON invite_links(room_id);
CREATE INDEX idx_invite_links_document ON invite_links(document_id);

CREATE TABLE sessions (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    color TEXT NOT NULL,
    role TEXT NOT NULL,
    scope_type TEXT NOT NULL CHECK (scope_type IN ('room', 'document')),
    room_id TEXT,
    document_id TEXT,
    created_at INTEGER NOT NULL,
    expires_at INTEGER NOT NULL,
    revoked_at INTEGER,
    FOREIGN KEY (room_id) REFERENCES rooms(id) ON DELETE CASCADE,
    FOREIGN KEY (document_id) REFERENCES documents(id) ON DELETE CASCADE,
    CHECK (
        (scope_type = 'room' AND room_id IS NOT NULL AND document_id IS NULL)
        OR
        (scope_type = 'document' AND room_id IS NULL AND document_id IS NOT NULL)
    )
);

CREATE INDEX idx_sessions_room ON sessions(room_id);
CREATE INDEX idx_sessions_document ON sessions(document_id);

CREATE TABLE document_updates (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    document_id TEXT NOT NULL,
    seq INTEGER NOT NULL,
    update_id TEXT NOT NULL,
    author_session_id TEXT NOT NULL,
    update_data BLOB NOT NULL,
    created_at INTEGER NOT NULL,
    FOREIGN KEY (document_id) REFERENCES documents(id) ON DELETE CASCADE,
    UNIQUE(document_id, seq),
    UNIQUE(document_id, update_id)
);

CREATE INDEX idx_updates_document_seq
ON document_updates(document_id, seq);

CREATE TABLE document_snapshots (
    id TEXT PRIMARY KEY,
    document_id TEXT NOT NULL,
    seq INTEGER NOT NULL,
    content BLOB NOT NULL,
    content_hash TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    FOREIGN KEY (document_id) REFERENCES documents(id) ON DELETE CASCADE,
    UNIQUE(document_id, seq)
);
```

`head_seq` --- последняя назначенная сервером последовательность.\
`persisted_seq` --- последний непрерывный seq, подтверждённый COMMIT.\
`snapshot_seq` --- seq, включённый в последний snapshot.\
`update_id` --- защита от повторной транспортной записи.

Для будущей истории нужно сохранять audit metadata: автора, имя и цвет
на момент принятия операции. Текущую сессию нельзя использовать для
отображения старой истории.

### 9.3. SQLite настройки

``` sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = FULL;
```

`FULL` выбран ради надёжности подтверждённых транзакций. Фактические
гарантии зависят от ОС, файловой системы, диска и fsync.

Один SQLite-файл не использовать как общую БД нескольких
backend-инстансов через сетевую файловую систему.

### 9.4. Group commit

Начальные параметры для эксперимента:

-   batch до 100 updates;
-   flush примерно каждые 50--100 мс;
-   немедленный flush при graceful shutdown.

Это не окончательные настройки. Их подбирают по p95/p99 задержке
сохранения и throughput. При низкой нагрузке таймер ограничивает
задержку, при высокой --- batch повышает пропускную способность.

## 10. Revision, hash и восстановление

Revision определяет порядок, SHA-256 проверяет целостность snapshot.

Пример:

``` text
head_seq       = 157
persisted_seq  = 150
snapshot_seq   = 120
```

Сервер принял updates до 157, записал до 150, последний snapshot
включает состояние до 120.

После COMMIT updates 151--157:

``` text
head_seq       = 157
persisted_seq  = 157
snapshot_seq   = 120
```

После создания snapshot:

``` text
head_seq       = 157
persisted_seq  = 157
snapshot_seq   = 157
```

Hash вычисляется по конкретному сериализованному snapshot. Он не
определяет новизну и не заменяет журнал.

### 10.1. Восстановление

1.  Загрузить последний валидный snapshot.
2.  Проверить hash.
3.  Загрузить updates с `seq > snapshot_seq` до `persisted_seq`.
4.  Применить их по порядку через Engine.
5.  Проверить восстановленное состояние.
6.  Открыть документ для новых соединений.

Если snapshot повреждён, использовать предыдущее валидное поколение и
журнал. Старые snapshots нельзя удалять до проверки нового.

### 10.2. Компактизация

1.  Создать snapshot на известном seq.
2.  Сохранить его.
3.  Проверить hash и возможность восстановления.
4.  Только затем удалять updates, покрытые snapshot.
5.  Сохранять запасное поколение snapshot.

Для MVP безопаснее сначала не удалять журнал автоматически.
Компактизацию включать после измерения размера БД и тестов
восстановления.

## 11. Автосохранение и жизненный цикл

### 11.1. Горячий путь

1.  Клиент создаёт Yjs update.
2.  Сохраняет update в IndexedDB.
3.  Отправляет update серверу.
4.  Gateway проверяет сессию, лимиты и формат.
5.  DocActor обрабатывает событие и назначает seq.
6.  Update рассылается участникам.
7.  Update передаётся Persistence Writer.
8.  Writer записывает batch в SQLite.
9.  После COMMIT обновляется `persisted_seq`.
10. Клиент получает ACK и может удалить локальную копию.

Broadcast может произойти до COMMIT, но UI не показывает `Saved` до ACK.
Если сервер упал до COMMIT, клиент повторно отправляет неподтверждённое
изменение из IndexedDB.

### 11.2. Уход последнего участника

``` text
ACTIVE
  |
  v
IDLE
  |
  | grace period
  v
FLUSHING
  |
  v
SNAPSHOTTING
  |
  v
UNLOADED
```

После ухода последнего участника:

1.  Документ переходит в `IDLE`.
2.  Запускается grace period, начально 30--60 секунд.
3.  При возвращении участника выгрузка отменяется.
4.  После grace period старый runtime прекращает приём новых операций.
5.  Ожидаются принятые persistence jobs.
6.  При необходимости создаётся snapshot.
7.  Проверяются revision и hash.
8.  Runtime освобождается.

Комната и документ остаются в БД. Snapshot не нужен при каждом закрытии,
если текущий уже покрывает `persisted_seq`.

Закрытие браузера не является гарантией сохранения. Периодический flush
работает независимо от ухода участников.

### 11.3. Graceful shutdown

-   перейти в drain mode;
-   прекратить новые подключения;
-   уведомить клиентов;
-   завершить принятые события;
-   сбросить persistence queue;
-   дождаться COMMIT в пределах timeout;
-   сохранить необходимые snapshots;
-   закрыть БД;
-   завершить процесс.

Go Channels находятся в RAM и не являются durable queue. Надёжность
обеспечивается ACK после COMMIT и клиентской IndexedDB.

## 12. Отказоустойчивость

  ---------------------------------------------------------------------
  Сценарий                           Реакция
  ---------------------------------- ----------------------------------
  Потеря сети                        Reconnect + CRDT resync

  Повторный update                   Дедупликация по update_id; CRDT
                                     остаётся идемпотентным

  Медленный клиент                   Ограниченная outbox, disconnect и
                                     resync

  Event queue заполнена              Backpressure / временный отказ

  Persistence queue заполнена        Не подтверждать сохранение,
                                     ограничить вход

  SQLite недоступна                  Ограниченные retry, degraded
                                     status

  Штатная остановка                  Graceful flush

  Аварийное падение до COMMIT        Повторная отправка
                                     неподтверждённого из IndexedDB

  Повреждение snapshot               Предыдущее поколение + журнал

  Перегрузка документа               Локальные лимиты и изоляция

  Массовое переподключение           Exponential backoff + jitter

  Диск заполнен                      Readiness false, degraded notice,
                                     запрет ложного ACK
  ---------------------------------------------------------------------

Нельзя обещать абсолютную сохранность при одновременной потере сервера и
клиентского устройства до подтверждения. Для более строгой серверной
гарантии можно добавить локальный durable journal --- отдельное
усложнение после MVP.

## 13. Производительность и цель 10 000 подключений

Цель --- архитектурная готовность к кластеру с 10 000 одновременных
WebSocket-подключений. Это не гарантия, что один Go-процесс с SQLite
выдержит такой профиль.

Отдельно тестировать:

-   10 000 подключённых, но неактивных клиентов;
-   10 000 клиентов с Presence;
-   1 000 активно редактирующих клиентов;
-   сотни участников одного документа;
-   тысячи участников одного горячего документа.

При полном broadcast N активных участников и N updates/сек могут создать
до N × (N − 1) доставок/сек. Это фундаментальная стоимость fan-out.

### 13.1. Стартовые лимиты

  Параметр                                    Стартовое значение
  --------------------- ----------------------------------------
  Подключения             Ступенчатые тесты до 10 000 на кластер
  UPDATE frame                          До 2 MiB, конфигурируемо
  Awareness frame                                       До 4 KiB
  Outbox клиента                              128--256 сообщений
  Awareness                                 До 20 Гц на документ
  Ping interval                                        30 секунд
  Write timeout                                         5 секунд
  Idle timeout                                         90 секунд
  Участники документа                        Начальный лимит 100

Размер STEP2 ограничивается `max_doc_bytes`. Один лимит 64 KB для всех
сообщений слишком мал и может ломать первичную синхронизацию и вставку
больших фрагментов. Все ограничения конфигурируемые и подтверждаются
тестами.

### 13.2. Admission control

-   лимит подключений на IP/сессию;
-   лимит сообщений в секунду;
-   лимит размера update;
-   лимит активных документов;
-   лимит участников документа;
-   ограниченные очереди;
-   ограничение памяти на документ;
-   контроль медленных клиентов;
-   справедливое обслуживание документов.

### 13.3. Sharding

Документы распределяются по shard workers по hash от document ID.
События одного документа всегда попадают к одному владельцу.

Шард не должен быть одной глобальной очередью, блокирующей все
документы. Нужны ограниченные inbox и независимое обслуживание.

## 14. Горизонтальное масштабирование

### MVP

``` text
Clients
   |
Docker
   |
Go Application (one instance)
   |
SQLite WAL (local persistent volume)
```

### Будущий кластер

``` text
                 Load Balancer
                /      |      \
             Go 1     Go 2    Go 3
                \      |      /
             Document Ownership / Routing
                         |
                  Durable Broker
                         |
                    PostgreSQL
```

**Document affinity:** один экземпляр владеет активным документом и
упорядочивает его updates.

Для failover одного consistent hash недостаточно. Нужны lease и fencing
token/epoch, чтобы старый владелец после сетевого разделения не
продолжал принимать изменения одновременно с новым.

Redis Pub/Sub может передавать эфемерные события, но не является durable
журналом. При нескольких экземплярах потребуется общее хранилище,
например PostgreSQL. SQLite-файл не использовать как общую БД нескольких
серверов через сетевую файловую систему.

## 15. История изменений и rollback --- следующий этап

История не входит в обязательный MVP, но архитектура оставляет для неё
путь.

Разделять:

-   **CRDT update journal** --- технический журнал синхронизации и
    восстановления;
-   **Document commits** --- логические версии, понятные пользователю.

Commit включает commit ID, document ID, parent commit ID,
revision/snapshot reference, автора, имя и цвет на момент изменения,
сообщение, время и diff/reference.

Изменения одного автора можно группировать за короткий период
бездействия, например 3--5 секунд. Это не должно менять порядок CRDT
updates.

Авторство нельзя определять только сравнением snapshots. Оно связывается
с исходной серверной сессией.

### Rollback

Откат не удаляет историю:

1.  Получить сохранённое состояние версии.
2.  Проверить права.
3.  Сформировать новую операцию восстановления.
4.  Применить её как новое CRDT-изменение.
5.  Распространить участникам.
6.  Сохранить update.
7.  Создать commit `Revert to ...`.

Нельзя просто заменить Yjs state старым snapshot. Rollback должен быть
новой CRDT-операцией.

Для rich text полноценный diff должен учитывать структуру ProseMirror.
Обычный текстовый diff годится только для упрощённого варианта.

## 17. Docker и эксплуатация

Рекомендуется multi-stage build:

1.  Сборка Go binary.
2.  Сборка frontend.
3.  Минимальный runtime image.
4.  Запуск без root.
5.  SQLite в persistent volume.
6.  Admin endpoints недоступны из публичной сети.

Разделить:

-   **Liveness:** процесс жив.
-   **Readiness:** приложение готово принимать запросы, writer и
    хранилище доступны, сервер не в drain.

SQLite-файл хранится в Docker volume. Для production нужны backups и
тест восстановления.

Litestream --- полезное P1-дополнение для репликации SQLite в
S3-совместимое хранилище. Сначала проверить WAL-конфигурацию и restore.
Репликация асинхронна: нельзя обещать нулевой RPO, нужно измерять
фактическое отставание.

### Реалистичный scope восьмичасовой разработки

За восемь часов следует стремиться к вертикальному срезу:

1.  Создать комнату.
2.  Войти двум-трём участникам по ссылке.
3.  Назначить цвета.
4.  Создать документ.
5.  Редактировать его одновременно.
6.  Показать курсоры.
7.  Сохранить updates в SQLite.
8.  Перезапустить сервер и восстановить документ.

История, сложный diff, rollback, Litestream, кластер и нагрузочный тест
на 10k не должны считаться гарантированно готовыми за это время.

## 19. Демонстрационные сценарии

**Комната:** пользователь создаёт комнату, получает ссылку, второй
входит, оба видят друг друга.

**Документ:** создаётся документ, участники получают разные цвета и
одновременно редактируют один абзац.

**Новый участник:** открывает документ, получает актуальное состояние и
видит присутствующих.

**Сохранение:** UI показывает `Saving`, после COMMIT приходит ACK и UI
показывает `Saved`; после перезапуска контейнера документ
восстанавливается.

**Переподключение:** клиент теряет соединение до ACK, сохраняет update в
IndexedDB, переподключается и повторно отправляет неподтверждённое
изменение.

**История (после MVP):** создаются commits, показывается diff, rollback
выполняется как новая операция.

**Нагрузка:** показываются подключения, throughput, задержки, очереди,
CPU и RAM.

## 22. Уточнения v3.1: инварианты, которые нельзя оставлять на усмотрение реализации

### 22.1. Комната, документ и приглашение

-   Комната --- рабочее пространство и точка входа участников.
-   Документ --- самостоятельная сущность с собственным CRDT-состоянием
    и журналом.
-   Связь комнаты и документа хранится в `room_documents`.
-   Прикрепление существующего документа означает совместное
    использование того же документа, а не копирование его содержимого.
-   Если понадобится перенос или копирование, это отдельные команды с
    явно описанной семантикой.
-   Приглашение --- отдельная запись `invite_links`. В URL находится
    случайный секрет, в БД хранится только его криптографический hash.
-   Приглашение имеет scope (`room` или `document`), роль,
    необязательный срок действия и отметку отзыва.
-   Для document-scope ссылка не должна автоматически давать доступ ко
    всем остальным документам комнаты.

### 22.2. Анонимная сессия

Анонимность означает отсутствие регистрации и пароля, но не отсутствие
идентичности сессии. После входа сервер выдаёт случайный `session_id`,
назначает имя/цвет и подписывает сессионный токен.

Для MVP рекомендуется хранить серверную запись сессии: `session_id`,
созданное имя, цвет, роль/scope, `created_at`, `expires_at`,
`revoked_at`. Подписанная cookie подтверждает целостность claims, но
серверная запись нужна для отзыва и контроля срока жизни. Не
использовать имя или цвет, присланные клиентом, как источник истины.

Сессия, созданная по room invitation, получает room scope; сессия по
document invitation получает document scope. При каждом HTTP/WS-доступе
проверяются срок действия, отзыв и фактический scope.

### 22.3. Идемпотентность update и ACK

Для каждого клиентского update клиент генерирует стабильный `update_id`
и сохраняет сам update вместе с ID в IndexedDB до отправки. При
повторной отправке после reconnect используются те же `update_id` и
payload.

В транзакции SQLite сервер: 1. проверяет уникальность
`(document_id, update_id)`; 2. если update уже существует, возвращает
ранее назначенный `seq`, не создавая новую строку; 3. если update новый,
назначает следующий `seq` и вставляет запись; 4. обновляет
`persisted_seq` только для непрерывного подтверждённого префикса; 5.
отправляет ACK только после успешного COMMIT.

ACK должен содержать как минимум `document_id`, `update_id`, `seq` и
`persisted_seq`. Клиент удаляет локальную копию только после ACK для
соответствующего `update_id`. Одного общего числа `acked` недостаточно,
если клиентские updates могут подтверждаться не по порядку.

`head_seq` нельзя считать durable watermark. После аварийного завершения
неподтверждённые значения `head_seq` должны быть восстановлены из
фактически сохранённого журнала, а не из RAM.

### 22.4. Последовательность обработки и persistence

DocActor --- единственный последовательный владелец runtime-состояния
документа. Он не должен ждать медленный WebSocket write или выполнять
SQLite I/O синхронно в основном цикле.

Важное правило: update не может считаться принятым сервером, пока он не
помещён в bounded persistence pipeline. При заполнении persistence queue
сервер применяет backpressure и не создаёт бесконечный разрыв между
broadcast и durable storage. Оптимистичная рассылка допустима только при
наличии чёткой семантики восстановления и повторной доставки.

Persistence Writer владеет транзакциями SQLite. Он возвращает результат
DocActor/координатору, после чего отправляется durable ACK. Если
подтверждения могут приходить пакетами, каждый ACK должен однозначно
покрывать конкретные `update_id`.

### 22.5. Синхронизация при подключении

Нельзя полагаться только на абстрактную последовательность «получить
snapshot, затем слушать updates». Регистрация соединения, фиксация sync
watermark и подписка на live updates должны быть атомарно упорядочены
относительно событий DocActor.

Тест обязателен: пока новый клиент получает начальное состояние, другие
клиенты непрерывно редактируют документ. После завершения handshake
новый клиент должен получить все операции без пропусков и без требования
перезагрузить страницу.

### 22.6. Snapshot и восстановление

Snapshot создаётся только из состояния, которое можно однозначно связать
с конкретным `seq`. Если Engine не умеет безопасно получить
согласованный snapshot на заданной границе, snapshot worker должен
запросить его у владельца документа через контролируемый механизм.

Восстановление выполняется из последнего проверенного snapshot и журнала
после `snapshot_seq` до `persisted_seq`. Нельзя восстанавливать
неподтверждённые операции только из `head_seq`.

### 22.7. Границы MVP

В MVP входят комнаты, приглашения, анонимные сессии, документы,
совместное редактирование, курсоры/presence, локальная очередь клиента,
durable ACK, SQLite persistence, восстановление после перезапуска и
базовые ограничения нагрузки.

Не входят в MVP: аккаунты, сложная ролевая модель, полноценные
commits/diff/rollback, совместная работа нескольких backend-инстансов,
Kubernetes и обещание 10k активных редакторов. Архитектура не должна
требовать их реализации заранее.
